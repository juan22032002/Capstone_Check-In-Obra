Check-In-Obra multi-tenant

Hoy el sistema atiende a una constructora sembrada por migración. Esta propuesta lo lleva a muchas PYMEs en la misma instalación, cada una con su propia base de datos, de modo que el inventario, las obras y los costos de una constructora nunca estén en la misma base que los de otra.

Punto de partida

El modelo ya tiene la forma de un sistema multi-tenant: Empresa es la raíz, el JWT lleva el claim empresaId y AccesoEmpresa.esPropio devuelve el mismo 404 para un recurso ajeno que para uno inexistente, así que nadie puede contar las obras de la competencia. Todas las empresas comparten hoy una sola base, y el aislamiento depende de que cada servicio se acuerde de pedirlo. Una observación recibida pide que las bases sean independientes por empresa, y esta propuesta la adopta.

Lo que ya existe

  • empresa_id en usuarios, obras, materiales y herramientas
  • Claim empresaId firmado en el JWT
  • PerteneceAEmpresa en las 17 entidades y un guardián único
  • Código de barras único por empresa, no global (V4)

Lo que falta

  • Dar de alta empresas: hoy solo existe la que siembra V2__seed_admin.sql
  • Una base por empresa y algo que elija cuál abrir en cada petición
  • Flyway corre sobre una sola base
  • La API conecta como postgres, un superusuario

Por qué importa

  • 48 comprobaciones a mano repartidas en 16 archivos
  • Basta un endpoint nuevo sin esPropio para filtrar datos
  • Los costos unitarios (V8) son información comercial sensible

Modelo elegido

Hay tres formas clásicas de separar clientes. La propuesta es una base de datos por empresa, dentro del mismo servidor PostgreSQL. Cada base tiene el mismo esquema y su propio usuario, y una base de catálogo guarda qué empresas existen y cómo conectarse a cada una. Con esto, un error de filtro en el código ya no alcanza a otra constructora: sus datos no están en la base que se abrió.

El costo es operativo: Flyway corre una vez por base y hay un pool de conexiones por empresa. Para decenas de PYMEs eso cabe en un solo servidor. Si algún día fueran cientos, convendría repartir las bases entre varios servidores, sin cambiar el modelo.

Arquitectura objetivo

Hay dos planos. El plano del tenant es lo que ya existe: la app Flutter y los servicios de dominio, siempre dentro de una empresa. El plano de plataforma es nuevo: da de alta empresas, asigna planes y suspende cuentas, y solo escribe en la base de catálogo. Entre los servicios y PostgreSQL aparece una pieza nueva, el enrutador, que abre la base de la empresa que viene en el token y ninguna otra.

Una petición, paso a paso

El filtro lee empresaId del JWT y lo deja en un TenantContext (ThreadLocal) que se limpia en un finally. El enrutador es un AbstractRoutingDataSource de Spring: su determineCurrentLookupKey() devuelve la empresa del contexto y entrega la conexión del pool de esa empresa. Los pools se arman al arrancar, leyendo la base de catálogo, y se agrega uno cada vez que se da de alta una empresa. No hay base por defecto: si no hay empresa en el contexto, la petición falla en vez de caer en una base cualquiera.

Defensa en capas

Separar las bases no vuelve innecesario el resto. Cada capa cubre el hueco de la anterior, y la tabla dice qué se escapa en cada nivel. AccesoEmpresa y la columna empresa_id se mantienen: no estorban, facilitan pasar de la base actual a las nuevas y sirven de red si el enrutador se configura mal en una prueba.

Si llega una constructora nueva

Es el caso que justifica todo lo anterior. Hoy, sumar una empresa significa escribir una migración a mano. Con este modelo, es una operación del plano de plataforma que no toca las bases de las demás.

Qué cambia en cada parte

Base de datos

  • Base de catálogo con empresas, planes, operadores y los datos de conexión de cada base
  • Una base checkinobra_<empresa> por constructora, con el esquema de siempre
  • Un usuario de PostgreSQL por base, sin superusuario y sin permisos en las otras
  • Un usuario aparte para Flyway, que solo usa el job de migración
  • Respaldo y borrado por empresa, con pg_dump de su base

Backend

  • TenantContext poblado en JwtAuthFilter, limpiado en finally
  • TenantRoutingDataSource (un AbstractRoutingDataSource) con un pool Hikari por empresa y sin base por defecto
  • Flyway programático: recorre el catálogo al arrancar y migra cada base
  • Rol PLATAFORMA y rutas /api/plataforma/** para el alta y la suspensión
  • Las tareas programadas fijan la empresa a mano antes de tocar datos

App móvil

  • Base drift por empresa (checkinobra_<empresaId>.sqlite), o se borra al cerrar sesión
  • Cada movimiento en cola guarda el empresaId con que se creó
  • Si la sesión actual es de otra empresa, la cola no se envía

Plan por fases

Cada fase deja el sistema funcionando y se puede desplegar sola. Mientras exista una sola empresa, el enrutador tiene un único pool y todo se comporta como hoy, así que el cambio se puede probar sin apuro antes de la segunda constructora.

Decisiones abiertas

Dónde vive el login

  • Para saber qué base abrir hay que saber de qué empresa es quien inicia sesión, y eso pasa antes del JWT
  • Propuesta: el catálogo guarda un índice de correo a empresa; el PIN se sigue validando en la base de la empresa
  • El correo de login queda único en todo el sistema; el RUT del trabajador pasa a ser único solo dentro de su empresa, y un maestro subcontratado puede estar en dos constructoras

Catálogo de materiales

  • Hoy cada empresa carga sus propios materiales y mermas
  • Un catálogo base de plataforma (placa yeso-cartón, perfiles, tornillos) ahorraría el alta inicial
  • Se copiaría a la base de la empresa al crearla, para que los precios sigan siendo propios

Decisiones tomadas en la fase 1 (MT1)

La tabla empresas de cada base

  • Cada base conserva una copia de una fila de empresas: la de su propia empresa, con el mismo id que tiene en el catálogo
  • Se descartó retirar las FKs: cuatro entidades la referencian (Usuario, Obra, Material, Herramienta) y AccesoEmpresa y la columna empresa_id se mantienen como segunda capa
  • Ese id es el que viaja en el JWT, así que el catálogo no necesita una columna aparte con "el id en la base"
  • Una empresa, una base: nombre_base es único en el catálogo

Qué hay en checkinobra_catalogo

  • Tablas planes, empresas (rut, nombre, plan, estado, base, usuario y referencia al secreto), operadores e indice_login (correo → empresa, en minúsculas)
  • Sus migraciones están en db/catalogo y las aplica el migrador. La API la usa como checkinobra_plataforma, que solo ve esa base; el rol de una empresa no puede conectarse a ella
  • El catálogo guarda env:NOMBRE_DE_VARIABLE, nunca la contraseña
  • Al arrancar, la API migra el catálogo, registra a la empresa de la base actual (idempotente: no pisa el plan ni el estado que fije la plataforma) y completa el índice sin reasignar un correo que ya sea de otra empresa

El primer administrador ya no viene en una migración

  • V2__seed_admin.sql salió de db/migration: el ADMIN se crea al dar de alta la empresa, no en cada base nueva
  • Mientras no exista el módulo de plataforma (fase 4), en una base vacía nace la primera empresa con su ADMIN al arrancar, con la clave de PRIMER_ADMIN_CLAVE y obligado a cambiarla
  • Las bases que ya aplicaron V2 la conservan en su historial; Flyway ignora la migración aplicada que ya no está (ignore-migration-patterns=*:missing)

Lo que todavía no hace

  • La API sigue abriendo una sola base: el catálogo se lee, pero no enruta (fase 2)
  • El índice de login se completa al arrancar; mantenerlo al crear usuarios llega con el login por empresa (MT4)
  • No hay alta de empresas ni su base propia (fase 4)

Decisiones tomadas en la fase 2 (MT2)

El enrutador

  • JwtAuthFilter llena el TenantContext con la empresa del token y lo limpia en un finally después de toda la cadena: IdempotenciaFilter corre más adentro y también usa la base
  • TenantRoutingDataSource no tiene base por defecto. Sin empresa en el contexto, o con una sin pool, lanza SinEmpresaEnContextoException
  • Un pool por empresa, armado desde el catálogo. La contraseña sale de la referencia env:VARIABLE; una empresa mal registrada se anota y no impide arrancar a las demás
  • Un token sin empresaId (antes, un NPE) o de una empresa sin base o suspendida es un token inválido: 401

El login pasa antes del token

  • Antes de autenticarse no hay empresa en el contexto. /api/auth/login la saca del índice del catálogo; /api/auth/login-pin recibe empresaId junto al id de usuario, porque los ids se repiten entre bases
  • El bloqueo por intentos incluye la empresa en su clave de cuenta por la misma razón
  • Crear un usuario reserva su correo en el catálogo antes de guardarlo, y lo suelta si guardar falla (dos bases, sin transacción compartida). Se compara sin distinguir mayúsculas
  • Mientras exista una sola empresa, login-pin sin empresaId se resuelve a esa: es lo que permite que una app anterior siga entrando
  • Además de abrir la base de la empresa pedida, el login comprueba que el usuario encontrado sea de ella: con una base por empresa siempre lo es, y si una base estuviera mal registrada o compartida, no se entra con la empresa equivocada (MT4)

Hibernate sin conexión por defecto

  • hibernate.boot.allow_jdbc_metadata_access=false, dialecto PostgreSQL explícito y ddl-auto=none: al arrancar no se abre ninguna conexión
  • Se pierde la validación del mapeo contra el esquema al arrancar. La suite de pruebas la conserva (validate contra su base) y el esquema de cada empresa lo garantizan las migraciones (fase 3)

Lo que sigue sin hacer

  • Un job que migre una empresa nueva al darla de alta, sin reiniciar la API (fase 4): hoy se migra al arrancar
  • Alta de empresas y de su base (fase 4): hoy la base de una empresa se crea fuera, y solo hay una
  • La purga de claves de idempotencia ya recorre las empresas con base abierta; si una falla, sigue con las demás

Decisiones tomadas en la fase 3 (MT3)

Flyway por cada base

  • spring.flyway.enabled=false: el Flyway de Spring Boot migra una sola base y necesita una conexión sin empresa. MigradorDeBases corre Flyway programático sobre la base de cada empresa activa del catálogo, con el usuario migrador
  • Todas las bases reciben las mismas migraciones (db/migration), así que quedan en la misma versión. Una base vacía queda con el esquema completo en ese paso; el registro de la base inicial la migra antes de crear su empresa
  • Se mantiene ignore-migration-patterns=*:missing para las bases que aplicaron V2, que ya no está

Si una base falla

  • El resultado queda en el catálogo (migracion_estado, migracion_error, migrada_en) y en el log
  • Esa empresa no tiene pool y sus tokens no valen, porque una base a medio migrar no debe servir peticiones. Las demás se migran y arrancan igual
  • Una base nueva empieza PENDIENTE y solo se abre cuando su migración sale OK
  • Orden en el arranque: registrar la base actual → migrar todas → abrir pools → crear el administrador → sincronizar el índice de login

Pruebas de aislamiento (MT5)

Dos bases, de verdad

  • AislamientoConDosBasesTest registra dos empresas en el catálogo, cada una en su base (la de la suite y una segunda, vacía, que se migra en la prueba), con el enrutador real y sin el resolutor compartido que usan las demás pruebas
  • Con el token de A, cada GET por id de un objeto de B responde 404 y cada listado responde 404 o vacío; los listados generales no traen nada de B
  • Sin empresa en el contexto, tocar la base falla por JDBC y por JPA, y una tarea programada sin empresa fijada también
  • Corren en la CI: el paso de roles crea la segunda base con CHECKINOBRA_BASES_EXTRA

Lo que demuestran

  • Estos casos pasan aunque un endpoint olvide filtrar por empresa: los datos de B no están en la base que abre el token de A. Con una sola base, GET /api/trabajadores?obraId= devolvía nombre y RUT ajenos (S-05); con dos bases, devuelve una lista vacía
  • Se comprobó con una mutación: si el resolutor entrega siempre la misma base, la suite detecta la fuga (con los datos de B en la respuesta de A)
  • AccesoEmpresa sigue siendo la segunda capa para una base con más de una empresa (la de las demás pruebas)
